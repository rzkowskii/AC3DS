The next handheld log showed that the untextured draw also timed out. The renderer now uses the main-memory base for its vertex and index buffers. This keeps offsets within the PICA200's 28-bit range throughout the New model's main memory. The startup path uses indexed triangles and a straight-line shader, following the draw pattern used by Kingdom3DS, and explicitly flushes each command list before queuing it. The startup log includes the GPU status register if the queue times out again.

The indexed build also stopped at the untextured draw. Its log read `busy=00000000`, so the PICA200 was idle and the P3D completion event never reached the queue. The cause is still unconfirmed on hardware. Startup now runs a staged check: screen clear, an empty command list, a plain triangle through a position-and-color probe program with Citro3D's default buffer base, the game vertex program, the projection-texture program, then the splash. Each stage waits for the GPU queue. A stage that never completes is named on the touch screen and in `clientlog.txt` with the GX submission count, the last GSP result and the GPU busy bits. The first command lists of each launch are saved as `profile/gpu-list-N.bin`.

The renderer changes that go with it: command lists are submitted the stock Citro3D way with no extra flush wrapper, every vertex program writes each output register in full exactly once, the homogeneous texture coordinate moved to a separate projection program that is bound only for water, and texture unit one is never enabled without unit zero. If a launch stops inside the projection check, the next launch disables that program and records it in `profile/gpu-projective.txt`. Delete that file to retry. Azahar passed the smoke and Venison water fixtures on this build in `build-azahar/probe-01` and `build-azahar/probe-venison-01`. Venison averaged 53.875 FPS in that run, below the earlier 57 to 59. Physical verification is pending.

The next handheld log passed every startup check: screen clear, empty list, minimal draw, game shader draw, projection draw and the splash. It went on through sound, configuration and models to `init: mainloop`, then stopped with no further log lines. The crash is now after startup, in the first frames or the first map load. Model cache entries are now kept 8-byte aligned. Odd-sized shadow data could leave the next entry misaligned, and the ARM11 faults on multi-word and VFP stores to it while Azahar does not. Whether this was the handheld fault is unconfirmed.

The handheld's Luma3DS dumps then identified the fault for both the probe build and the alignment build. Each was a data abort with DFSR `0x801`, an alignment fault on a write. It came from a `stm` in `vertmodel::mesh::render` while `rendermapmodels` drew stencil shadows, writing the shadow-direction vector into a cache entry at an address 2 bytes off a word boundary. Rounding the allocation did not help, because the shadow-volume builder then trims each entry to its exact index data. That is 6 bytes per silhouette edge, so an odd edge count misaligns the next entry. The builder now adds one degenerate triangle when the edge count is odd, and the allocator rounds each next entry up to 8 bytes. Azahar passed the smoke fixture on this build in `build-azahar/shadowfix-02`. Handheld verification is pending.

- **SD probing:** every asset lookup checked the SD profile folder first, costing an FS IPC `stat` each time. The folder is now listed once into an index, and paths missing from it skip the probe.

World textures decode ahead on core 2 while the main thread helps. Azahar runs all cores on one host thread, so the parallel gain is unmeasured there.

Checking 27 candidate causes, each twice, refuted the coherency and stencil theories. Citro3D queues mid-frame splits and starts the GPU only at `C3D_FrameEnd`, after the arena flush.

The best-supported mechanism is that AssaultCube clears the top colour buffer only outside the map. **Grey screen on hardware, and fog parity (build 11, 2026-11-14)**

*Report.* On build 10, playing online on `ac_douze`, the handheld view sometimes went almost entirely flat grey ("like the camera is having an issue"), with only the hud gun, HUD, radar and a nearby pickup still clear. An earlier `ac_urban` screenshot taken on the handheld shows the same haze: the end of a 30-60 unit alley is nearly solid fog colour.

*Cause.* Fog. The PICA fog table has 128 entries indexed by stored depth. With the hyperbolic Z-buffer (near 0.15, far `fog*5/2`), the first entry covered everything from about 19 units to the far plane. Fog was interpolated across that one entry, so a wall 50 units away was about 64% fog colour and one 100 units away about 83%. Desktop AssaultCube's linear fog starts at `(fog+64)/8`, about 51 units with fog 350, and is 16% at 100 units. Looking across an open area therefore turned the whole view fog-coloured. This is deterministic, so Azahar shows it too. It was most visible on the handheld's LCD.

*Fix.* Perspective draws now use the PICA W-buffer. Stored depth falls linearly with eye distance (0.96 at the eye to 0 at the far plane), so the fog table spans distance evenly and reproduces desktop fog. The hud gun gets the 0.96-1 band in front of the world, which replaces desktop Cube's squeezed gun depth range. Polygon offset and the GPU aim depth convert to the new mapping. Ortho, oblique (water clip) and other projections keep the Z-buffer. `ac3dslineardepth 0` restores the old mapping for an A/B test.

*Azahar checks.* `ac_douze` matching poses before and after: far walls and sky keep their colour (PC preview for comparison). The GPU aim distance matches the CPU ray cast at 1.2-42 units. The gun stays in front of a wall at 1.2 units. Venison water reflection and refraction look the same apart from the lighter fog. Six bots on `ac_arctic2` ran at 59.9 FPS with shadows (stationary view). The handheld result is pending.

*Release package.* The public release is the engine-only build (`-DAC3DS_EMBED_ASSETS=OFF`) with the port's own launcher icon (`source/3ds/icon.png`). Players stage the game files from the official archive with `stage-assets.py`. In Azahar the engine-only build ran from freshly staged SD files and loaded `ac_douze` in 2.9 s. On the release build, Azahar measured `ac_arctic2` with six bots at 59.8 FPS (p99 20.5 ms, no missed VBlanks; stationary view, world batch reused on every frame) and `ac_venison` with eight bots at 54.2 FPS (p99 24.3 ms; both water effects were enabled, but neither water pass ran in that sample).

**Review of the port: see-through walls, two crashes, memory and audio (build 12, 2026-11-19)**

*Reports.* On build 11 (New 2DS XL) the game ran well, but sometimes the world showed through walls: players behind walls and the sky around the map were visible. There were also two crashes, one during gameplay and one after making a HOME Menu shortcut. Only one report survived, because `crash.txt` held the latest only. Build 12 follows a review of the whole port. Everything below was checked in Azahar; none of it has run on the handheld yet.

*Startup crash: explained, fixed in the build.* The surviving report is a data abort in `ac3ds_gl_init()` at init "video: mode": `ldr r1,[r2]` with r2 = 0 at pc `0x2a8f38` of the engine-only build 11 ELF. The game was being compiled `-fPIE` by accident: SDL_image's CMake file turns `CMAKE_POSITION_INDEPENDENT_CODE` on for the whole project. The code therefore reached a few globals through a global offset table, and `3dsxtool` cannot relocate GOT-relative references. Such a `.3dsx` only runs when the loader reproduces the linked distance between code and data. The registers fit a loader that did not: r5 is the link-time GOT address, while r6 (`&pixels`, a reference that is relocated) is one page above its link address, so the code read zeros from the page below the real table. The Homebrew Launcher keeps the linked layout, which is why normal launches worked. The shortcut tool is unknown and the one-page shift rests on a single digit of a transcribed report, so this is the best-fitting explanation, not a proven one. `CMakeLists.txt` now forces position-independent code off and a post-build step (`cmake/check-relocs.cmake`) fails the build if GOT-relative relocations return. The code segment is 187 KB smaller.

*Gameplay crash: two causes reproduced and fixed.* The handheld's report was lost, so which of the two it was is unconfirmed. Both were found in Azahar with eight bots and the handheld's own settings.

(1) Waypoint files with a wrong count, since build 10. Eight of the eleven stock waypoint files that carry a blank map name (`ac_alcove`, `ac_dusk`, `ac_kazemat`, `ac_lotus`, `ac_nocturne`, `ac_origin`, `ac_rampart`, `ac_toxic`; six of them are in the bot map menu) state a waypoint count three to fourteen times the records they hold: they were saved after their flood-filled waypoints had been filtered, with the count from before. PC rejects these files for the blank name and never reads them. Build 10 started using them, and its loader ran off the end of the file: on `ac_toxic` it built 8,611 waypoints from a file that holds 893, loaded none of the real paths, and took the number of paths from an uninitialised variable, so some loads added 184,000 path links. In Azahar that raised the small-block count from 44,000 to 280,000 and ended in "out of memory"; whatever the count, bots on those maps had no usable paths. The loader now takes the count from the records: the one for which node and path records end exactly at the end of the file, with every path record starting from its own node. All 44 stock files load that way (36 as before, 8 corrected); a file whose records do not add up is refused and the map floods waypoints as on PC. One bot match on one of those six maps was enough to trigger it, which makes this the likeliest cause of the handheld crash.

(2) The heap running out over map changes. A bot rotation ended on the seventh map change with "out of memory (operator new failed)": heap arena 69 of 72 MB, 19 MB of it free but in pieces. A heap tracker (`-DAC3DS_HEAPTRACK=ON`, `ac3dsheap`) showed retention and fragmentation. Retention: each of the seven world-batch slots kept a vertex buffer grown for the largest view so far (up to 3 MB each after the whole-map minimap render), because slots and the working buffer swapped storage, and per-map tables kept the size of the largest map visited. A newly cached batch now gets an exact-size copy, and that storage is released at every map change. Fragmentation: the game keeps 50,000 to 100,000 blocks under 512 bytes alive, and devkitARM's `malloc` turns every request of 32 bytes or more into `memalign(32)`, which also splits off a leftover chunk each time. Free memory ended up in hundreds of 16-256 KB holes with no free block over about 1 MB, so each large request extended the heap until it hit the limit. What changed:
- Blocks of up to 512 bytes come from a dedicated 6 MB pool (`source/3ds/smallpool_3ds.cpp`: 4 KiB pages per size class, 32-byte classes that keep malloc's cache-line alignment). A page whose blocks are all free goes back to the pool for any class. About 2,000 blocks remain in the general heap.
- Each bot's per-waypoint records come from one block per bot. They were two heap blocks per waypoint per bot (58,000 on `ac_coal` with eight bots).
- The 5.6 MB world array of a 512-square map is one persistent buffer, the built-in server's scratch buffer is 1 MB (map size 9 at most) instead of 4 MB, and the working vertex buffer keeps 3 MB for the life of the process instead of being regrown by doubling at every map start.
- Strip index lists are released at every map change. Kept across maps and grown wherever they happened to be, they held more holes open than anything else (3.5 MB of holes per sample, now 0.1 MB).
- The world batch cache keeps 2 MB of heap unclaimed (`ac3dsheapreserve`, in KB), as it already did for linear memory. With the reserve gone it gives every cached batch back and draws by traversal until there is room again; an allocation the cache cannot have is no longer fatal. Forcing this on `ac_douze` and on `ac_venison` with water (reflection, and refraction on) gave pixel-identical frames with the cache given back, with single copies refused, and after it refilled; the `ac_venison` views ran at 42 to 54 FPS without the cache and 59.8 with it.

Result, 30-map rotations with eight bots on the final binary: the rotation that ran out of memory on its 31st map now completes with at least 9.6 MB of the 72 MB heap unclaimed; one with `ac_venison` as every other map (15 visits) completes with at least 8.2 MB. A sweep of all 44 stock maps with eight bots, 22 per run, loaded and played every one. Across these runs the pool peaked at 2.6 MB with no request refused, and the cache never had to give anything back. Unclaimed heap still falls by about 0.3 MB per map on average (sound blocks and map models that outlive their map hold the remaining holes open), so a much longer session reaches the reserve on the largest maps; from there the cost is frame rate, not a crash.

*Through walls: not isolated.* Three candidates were addressed. (1) The occlusion ray table was traced from the previous camera: `gl_drawframe()` only switches to the death, follow or fly camera after the table is built. Every death and respawn drew one frame without the facing walls, and a followed player turning more than about 4 degrees per frame opened a band of missing world. That is upstream behaviour that 100+ FPS hides; the camera is now chosen before the rays are traced. (2) Build 11 was the first to use the PICA W-buffer, the only depth change since build 10. The port's W path is self-consistent and Azahar never showed a fault, so the W-buffer is suspected, not shown. Depth is back on the Z-buffer of builds 1-10. (3) World detail followed desktop's fps feedback, which at a 60 fps cap only ratchets down to `minlod` (100 with the handheld's settings) while the emulator's default profile stayed at 250. Detail is now `minlod` on 3DS, the same on both. In Azahar with the handheld's own `saved.cfg`, 192 spawn-point views on four maps showed no difference between 100 and 250, so this is unlikely to be the report. If it happens again: `ac3dscleardebug 1` clears to magenta, so "nothing drawn here" cannot be mistaken for fog; `ac3dsmark` logs the camera pose and draw counts for replay with `ac3dspose`; `ac3dsworldcache 0` runs the upstream world traversal; `ac3dslineardepth 1` and `ac3dspixelfog 0` restore build 11's depth and fog.

*Fog.* Fog no longer reads stored depth. The vertex shader writes `u = .5 + .5*(e - start)/(end - start)` (e = eye distance) to texcoord2, the procedural texture unit maps it through a fixed table to GL's linear fog amount, and one combiner stage mixes in the fog colour. Same poses against build 11's fog on `ac_venison` (fog 180, 110 and 64), `ac_sunset` and `ac_arctic2` differ by 0.0-0.5 colour levels on average; build 10's fog differs by 4-11. The port had never used the procedural unit on hardware, so startup runs a guarded check (`profile/gpu-pixelfog.txt`, like the projection check). If a launch stops inside it, the next launch falls back to build 11's rendering; deleting the file retries.

*Audio.* NDSP was fed two 19.6 ms blocks, refilled once per frame, so any frame over 19.6 ms ran the channel dry. The queue is now three to five blocks, following recent frame time (three at 60 fps, four at 30, five at 20), at the cost of 20 ms more latency at 60 fps.

*Memory.* Map previews: every highlighted row in a map list left a 256 KiB texture allocated (up to 11 MiB); one stays resident now, and browsing all 44 twice leaves linear memory unchanged. The three font atlases are grey with alpha and upload as luminance-alpha, 2 MiB less. World geometry caches leave 2 MiB of linear memory free and are given back under pressure. A texture that fails to reload is no longer re-read and re-decoded on every draw.

*Robustness.* The keepalive thread is stopped before ENet is torn down when the game is closed from the HOME Menu (libctru runs no restore hook on that path), and stops by itself after three minutes in the HOME Menu or the software keyboard, since ENet queues every packet that arrives meanwhile. A frame is not opened without the GPU right (HOME, then Close, during a network wait). Settings are only written, and the five backups only rotated, when the text changed. QA teleport commands refuse to run on a server. Maps are limited to 512 squares (size 9) on the client as well as on the built-in server, the size the buffers above are planned for; `newmap` clamps to it. A server on a larger map is reported once ("map size 10 is not supported on 3DS") and the console waits for the next map instead of fetching the map again and again; in co-op editing, where the others would hold a different map, it leaves the session. Stored xmaps of an illegal size are skipped. `xmap_restore` no longer frees the world buffer (it is the persistent one now), and loading a stored xmap file allocates the world size instead of sixteen times that. The built-in server's map reader clamps a run length to the end of its buffer.

*Diagnostics.* Reports rotate five deep (`crash-1.txt` is the newest earlier report; the same for `stall.txt`). Crash and fatal-error reports carry the run-time addresses of text, data and bss markers; those and stall reports carry the map, heap figures sampled every 512 frames against the heap limit, and the last eight log lines. `scripts/symbolize-crash.py` checks the instruction words and the markers against the ELF, refuses a mismatch, reports a data segment the loader moved, and can find the matching ELF under `build*/`. The memory log line shows the heap unclaimed now and the lowest that has ever been, the small-block pool's use of its 6 MB, and how many requests the pool had to pass on to the heap because it was full. A fatal-error report (out of memory, abort, library panic) now lists the callers on its stack, the size of the last request that failed with the frame it failed in, and the pool figures. The startup checks record a pass with the build number, so each new build runs them under the guard once.

*Performance.* All Azahar, which does not model GPU time. Earlier figures on this page are stationary views with the world batch reused on every frame, and the two Venison "both water passes" figures ran no water pass in the sample. `ac3dsbench` now gives a moving-camera figure: it stands at a fixed spot, turns the view 2.713 degrees every frame so no view repeats, and profiles 240 frames per renderer option. With six idle bots `ac_douze` runs at 59.8 FPS (p99 19.1 ms) with a 10.4 ms draw (world 7.6 ms, stencil shadows 1.2 ms); `ac_venison` with eight idle bots runs at 59.8 FPS (p99 17.5 ms) with a 7.2 ms draw. On the same run the upstream world traversal (`ac3dsworldcache 0`) costs 8.5 ms against the port's 7.6 ms, and `ac3dssharedworldverts 1` saves 0.4 ms on `ac_douze`; it stays off until timed on the handheld, like `ac3dsfastvertexoffsets`. Changes in this build: the second stencil pass skips casters the first pass culled; static map models keep 64 lit-vertex sets instead of 8, so a model placed more often than that is no longer relit every pass; the ray table and world batches are reused while standing still on a server (they were rebuilt every frame online); the main pass only records its cell selection when a reflection pass can use it. On the console the same command (about two and a half minutes, offline) logs `AC3DS_BENCH` / `AC3DS_PERF` / `AC3DS_PHASE` / `AC3DS_GPU` lines with real GPU times. Loading another map or going online cancels the run in that frame, and either way the player's own settings are put back; the run changes no saved setting at any point (stencil shadows are switched off for two variants through an unsaved override), so closing the game in the middle leaves `saved.cfg` as it was. A variant too slow to collect its 240 frames reports the frames it has.

*Parity check.* Fixed poses on `ac_douze`, `ac_sunset` and `ac_desert` are pixel-identical before and after the review changes (one `ac_sunset` view differs by 0.02 colour levels on average), as were three `ac_venison` views with water reflection checked earlier in the review. `ac3dssharedworldverts 1` and `ac3dscleardebug 1` leave a normal view unchanged. The later memory changes (pool, vertex buffer, strip lists, cache reserve) leave the fixed `ac_venison` view with water pixel-identical as well.

*Handheld, build 12 (New 2DS XL, 2026-11-20).* One short session, read from the card's log. Both startup checks passed, the new per-pixel fog draw included (`gpu-pixelfog.txt` and `gpu-projective.txt` read `ok 12`). The game then joined a public server, fetched the custom map `ac_nest` from it, played CTF for about 90 seconds at 13 to 17 ms per logged frame and left by choice. The heap kept 28.1 MB unclaimed at its lowest, the small-block pool held 1.4 MB with nothing refused, and no crash or stall report was written. It says nothing yet about see-through walls, long sessions or bot matches.

**Map change that fetches content while online (build 13, 2026-11-20)**

*Report.* Read from the handheld's own build 11 log, not from a crash report: on 16 November, on a public server, the map changed to the custom map `ac_inca`. The load took 102 seconds, 96.8 of them in the stage that fetches missing content from the package server and installs it on the card. `stall.txt` recorded a main loop that did not advance for 107 seconds, and the connection was dropped about 20 seconds after the game came back. It looks like a crash and is not one. The log does not say how those 96.8 seconds divide between the transfers and the card: successful downloads were not logged.

*Causes found in the code.* (1) Nothing serviced the game connection during that stage. Upstream services it between load stages only, which a PC download finishes well within; ENet gives up on a peer that acknowledges nothing for 30 seconds. (2) Each installed file cost about eight SD operations on top of its data: a stat of its folder, a staged file made with `mkstemp` (which stats the folder again), a sync, two stats for an old copy and a backup, and a rename. On the handheld each is an IPC round trip of 25 to 100 ms. (3) The address of the package server was looked up again at every map load, a blocking call. (4) The loading screen was redrawn for every block received. (5) START did not cancel: `interceptkey()` read the buttons before noting where to start scanning the event queue, so it skipped the very presses it had just queued. That also affected cancelling the server list and the dedicated server's stop key.

*Changes.* The download progress callback and the install loop service the connection (at least four times a second during transfers, once per file). Files new to the card are written beside their target and renamed when complete, with no stats and no sync (four SD operations instead of eight); folders already seen on the card are not checked again. The startup lookup of a listed package server is reused. The screen is drawn ten times a second at most. `interceptkey()` scans the presses it queued, so START cancels. And the wait is bounded: `ac3dsdownloadwait` (default 30 seconds, counted from the start of the map load, only while connected) gives up the remaining downloads and plays the map without them; the next load of that map fetches what is still missing. The bound is needed even with the connection serviced: a stock server kicks as AFK, about 48 seconds after a map change, a player who has not spawned yet when five or more are on in a team mode or the server is full. Each package now logs its lookup, transfer and install times, so the next handheld log shows where the time goes.

*Emulator evidence.* A local game server built from this source, a custom map that needs one 21-file model package, and a package server throttled to a 41-second transfer. Build 12: the server dropped the client 45 seconds after it joined, as on the handheld. Build 13 with the limit off: the 43-second load completed and the client stayed connected until it quit. Build 13 with the default limit: the download was given up, the map loaded 30.2 seconds after the change and the client stayed connected. Installing the 21 files took 3.4 seconds before and 1.7 after; Azahar's SD timing is not the handheld's, so the ratio on the card is not known. START cancelling was verified by reading the code only: the test harness cannot press it during a load. The regression script and a 14-map soak pass on this build.
